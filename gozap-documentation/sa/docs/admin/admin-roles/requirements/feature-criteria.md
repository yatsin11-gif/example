# Критерии

## Источник

- Feature spec: `sa/docs/admin/admin-roles/requirements/feature-spec.md`
- Утвердил: Не утверждено; draft подготовлен по запросу SA
- Дата: 2026-06-30
- Репозитории в скоупе: `gozap-admin`, `gozap-backend`

## Цель

- Супер-админ должен иметь возможность создавать администраторов и назначать им уровень доступа.
- Администратор должен видеть в админке только те разделы, которые соответствуют его уровню доступа.

## FE Criteria

### Затронутые поверхности

- `gozap-admin`: раздел управления администраторами (доступен только супер-админу), навигация админки с условной видимостью разделов.

### Пользовательские сценарии и состояния

#### Создание администратора (супер-админ)

- Супер-админ должен иметь возможность создать нового администратора.
- При создании администратора супер-админ должен выбрать для него уровень доступа из доступного списка.
- Форма создания администратора не должна позволять сохранение без выбранного уровня доступа.

#### Вход и навигация (администратор)

- Администратор должен иметь возможность войти в админку.
- После входа администратор должен видеть только разделы, доступные его уровню доступа.
- Администратор не должен видеть в навигации пункты меню для недоступных разделов.

### Правила пользовательского поведения

- Супер-админ видит и может управлять всеми разделами без ограничений.
- Администратор не должен иметь возможность изменить собственный уровень доступа.

### Ограничения и исключения на FE

- Критерии не фиксируют точный список разделов и уровней доступа сверх «супер-админ = всё, админ = ограниченный набор» (см. открытые вопросы).
- Критерии не требуют интерфейса аудит-лога действий администраторов.

## BE Criteria

### Затронутые backend области

- `gozap-backend`: учётные записи администраторов, роли и уровни доступа, авторизация запросов по уровню доступа.
- Внешние интеграции: N/A.

### Правила бизнес-логики и обработки

#### Создание администратора

- Backend должен поддерживать создание учётной записи администратора только от имени супер-админа.
- Backend должен сохранять выбранный уровень доступа при создании администратора.
- Backend должен отклонять создание администратора без указанного уровня доступа.

#### Авторизация по уровню доступа

- Backend должен проверять уровень доступа администратора при обращении к разделам/эндпоинтам, ограниченным ролевой моделью.
- Backend не должен возвращать данные разделов, недоступных текущему уровню доступа администратора.
- Backend должен разрешать супер-админу доступ ко всем разделам без дополнительной проверки уровня.

### Побочные эффекты и интеграционные результаты

- Платежи: N/A.
- Подписка / доступ: доступ администратора к разделам определяется уровнем доступа, заданным супер-админом.
- Аналитика: Не определено.
- Email / CRM / webhooks: Не определено.

### Ограничения и исключения на BE

- Критерии не фиксируют точную схему хранения ролей/permissions.
- Критерии не требуют поддержки делегирования роли супер-админа.

## Нефункциональные критерии

### FE

- Производительность: Не определено.
- Доступность: разделы, недоступные уровню доступа администратора, не должны быть доступны прямым переходом по URL.
- Консистентность UX: единый паттерн отображения/скрытия разделов навигации по уровню доступа.

### BE

- Надежность: Не определено.
- Наблюдаемость: backend должен различать ошибки аутентификации (неверный логин/пароль) и ошибки авторизации (недостаточный уровень доступа).
- Безопасность: проверка уровня доступа должна выполняться на backend, а не только скрытием элементов на FE.

## Вне scope

- Гранулярные права на уровне отдельных действий внутри раздела.
- Аудит-лог действий администраторов.
- Делегирование/передача роли супер-админа.
- Создание или изменение Qase test cases.

## Открытые вопросы

- Какой конкретный список уровней доступа и разделов нужно поддержать?
- Нужна ли возможность редактировать уровень доступа у уже созданного администратора?
- Что должно происходить при прямом обращении администратора к недоступному разделу — ошибка 403, редирект или скрытие пункта меню?

## Примечания

- Критерии подготовлены на основе draft feature spec и входных SA-заметок по ролям в админке.
- FE отвечает за форму создания администратора и условную навигацию по уровню доступа.
- Backend отвечает за хранение ролей/уровней доступа и серверную проверку доступа к разделам.
