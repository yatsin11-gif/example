# Критерии

## Источник

- Feature spec: `sa/docs/gozap/partners-admin/requirements/feature-spec.md`
- Утвердил: Не утверждено; draft подготовлен по запросу SA
- Дата: 2026-06-30
- Репозитории в скоупе: `gozap-admin`, `gozap-backend`

## Цель

- Администратор должен полностью управлять партнёрами, привязкой станций и процентом отчисления.
- Партнёр должен видеть только свои данные и получать выплаты автоматически раз в месяц через Stripe.
- Поставка считается корректной, если баланс партнёра корректно отражает аренды только за период привязки станции.

## FE Criteria

### Затронутые поверхности

- `gozap-admin`: раздел "Партнёры" (список, создание, поиск/фильтр, привязка/отвязка станций, процент), кабинет партнёра (станции, сводка, история, выплаты, настройки счёта).
- `gozap-station-app`: `N/A`
- `gozap-backend`: `N/A` (раздел FE не применим к backend)

### Пользовательские сценарии и состояния

#### Создание и список партнёров (admin)

- Администратор должен иметь возможность создать партнёра с полями: логин, пароль, имя, телефон.
- Администратор должен видеть список партнёров с возможностью поиска и фильтрации.

#### Привязка станций к партнёру (admin)

- Администратор должен иметь возможность привязать одну или несколько станций к партнёру.
- Администратор должен иметь возможность отвязать станцию от партнёра.
- Администратор должен иметь возможность задать процент вознаграждения отдельно для каждой станции, включая значение 0%.

#### Зеркало кабинета партнёра (admin)

- Администратор должен видеть те же данные, что видит партнёр, по каждому партнёру и станции.

#### Кабинет партнёра — список станций

- Партнёр должен видеть список своих станций: код, название, адрес, статус.
- По каждой станции партнёр должен видеть количество аренд и сумму вознаграждения за выбранный период.

#### Кабинет партнёра — сводка за период

- Партнёр должен видеть текущий баланс, размер ближайшей выплаты, число завершённых аренд, сумму вознаграждения и разбивку по станциям за выбранный период.

#### Кабинет партнёра — детали станции

- Партнёр должен иметь возможность открыть конкретную станцию и увидеть список аренд за период: дата, стоимость, вознаграждение партнёра, и итоговую сумму.

#### Кабинет партнёра — счёт и выплаты

- Партнёр должен иметь возможность один раз указать банковский счёт/карту и отредактировать его при необходимости.
- Партнёр должен видеть историю выплат: суммы и даты.
- Партнёр должен иметь возможность выгрузить CSV по заработку и выплатам.

#### Сброс пароля

- Партнёр должен иметь возможность сбросить пароль через SMS-код на свой номер телефона.

### Правила пользовательского поведения

- Партнёр не должен видеть данные станций, не привязанных к нему.
- Список и сводка партнёра должны фильтроваться по выбранному периоду.
- CSV-выгрузка должна соответствовать выбранному периоду на экране.

### Ограничения и исключения на FE

- Критерии не фиксируют точный визуальный дизайн экранов админки и кабинета партнёра.
- Критерии не требуют ручного запроса выплаты партнёром.
- Критерии не требуют email/push уведомлений.

## BE Criteria

### Затронутые backend области

- `gozap-backend`: модель партнёра, привязка станций к партнёру с историей периодов, расчёт доли вознаграждения по завершённым арендам, баланс партнёра, ежемесячный payout job, хранение банковских реквизитов, история выплат.
- Внешние интеграции: Stripe (выплаты), Twilio (SMS для сброса пароля).

### Правила бизнес-логики и обработки

#### Управление партнёрами и станциями

- Backend должен хранить партнёра с логином, хэшем пароля, именем и телефоном.
- Backend должен поддерживать привязку и отвязку станции к партнёру с фиксацией даты начала и конца привязки.
- Backend должен хранить процент вознаграждения отдельно для каждой пары "партнёр-станция", включая 0%.

#### Расчёт баланса

- При завершении аренды backend должен определить, был ли привязан партнёр к станции в момент завершения аренды, и если да — начислить долю в баланс этого партнёра.
- Backend не должен пересчитывать начисления по станции при последующей отвязке/привязке к другому партнёру; начисления остаются привязанными к периоду, когда они были рассчитаны.
- Backend должен агрегировать баланс, число аренд и сумму вознаграждения по периоду и по станции для сводки партнёра.

#### Выплаты

- Backend должен запускать автоматическую выплату накопленного баланса партнёру один раз в месяц.
- Backend должен использовать Stripe для перевода средств на указанный партнёром счёт/карту.
- Backend должен хранить историю выплат (суммы, даты, статус) для отображения партнёру.
- Если банковский счёт/карта партнёра не указаны на момент плановой выплаты, backend не должен выполнять перевод и должен сохранить причину пропуска выплаты.

#### Сброс пароля

- Backend должен отправлять одноразовый код через Twilio на номер телефона партнёра для сброса пароля.
- Backend должен подтверждать сброс пароля только по корректному и не просроченному коду.

### Побочные эффекты и интеграционные результаты

- Платежи: ежемесячные выплаты партнёрам выполняются через Stripe; точная Stripe-сущность (Connect account / transfer) не подтверждена.
- Подписка / доступ: `N/A`
- Аналитика: Не определено.
- Email / CRM / webhooks: сброс пароля использует Twilio SMS; webhook от Stripe о статусе выплаты должен обновлять историю выплат.

### Ограничения и исключения на BE

- Критерии не фиксируют точную схему таблиц или внутренние имена сущностей Stripe/Twilio.
- Критерии не покрывают ручной запрос выплаты партнёром.
- Критерии не покрывают многоуровневую партнёрскую иерархию.

## Нефункциональные критерии

### FE

- Производительность: список партнёров и сводка должны оставаться отзывчивыми при росте числа станций.
- Доступность: понятные состояния отсутствия данных за период (нет аренд, нет выплат).
- Консистентность UX: одинаковое представление данных в admin-зеркале и в кабинете партнёра.

### BE

- Надежность: расчёт баланса не должен зависеть от порядка отвязки/привязки станций.
- Наблюдаемость: backend должен различать ошибки Stripe-выплаты и отсутствие реквизитов у партнёра.
- Безопасность: реквизиты банковского счёта/карты партнёра должны храниться и передаваться по правилам Stripe, без прямого хранения чувствительных данных карты в `gozap-backend`.

## Вне scope

- Изменение процента партнёром самостоятельно.
- Ручной запрос выплаты.
- Многоуровневая партнёрская иерархия.
- Email/push уведомления.
- Создание или изменение Qase test cases.

## Открытые вопросы

- Что происходит с накопленным балансом, если реквизиты не указаны на момент плановой выплаты — переносится на следующий месяц или блокируется до настройки?
- Какая именно Stripe-сущность используется для перевода средств партнёру?
- Может ли один партнёр иметь больше одного логина?

## Примечания

- Критерии подготовлены на основе draft feature spec и входных SA-заметок (CSV) по партнёрской программе Gozap.
- `gozap-admin` отвечает за UI управления партнёрами, зеркало данных и кабинет партнёра.
- `gozap-backend` отвечает за модель партнёра/станции, расчёт баланса, Stripe payout job и Twilio сброс пароля.
