# Критерии

## Источник

- Feature spec: `sa/docs/gozap/terminal-rental-app/requirements/feature-spec.md`
- Утвердил: Не утверждено; draft подготовлен по запросу SA
- Дата: 2026-06-30
- Репозитории в скоупе: `gozap-station-app`, `gozap-backend`

## Цель

- Пользователь должен арендовать powerbank через терминал станции основным потоком (номер + SMS + карта) или упрощённым потоком (только карта) для разряженного телефона.
- Поставка считается корректной, если powerbank выдаётся только после успешной оплаты, а аккаунт и карта сохраняются для будущих аренд.

## FE Criteria

### Затронутые поверхности

- `gozap-station-app`: экран покоя, экран ввода номера телефона, экран ввода кода из SMS, экран привязки карты, экран обработки оплаты, экран успеха/ошибки, упрощённый поток для разряженного телефона.
- `gozap-admin`: `N/A`

### Пользовательские сценарии и состояния

#### Экран покоя

- Терминал должен показывать основной интерфейс с полем ввода номера телефона.
- Терминал должен показывать менее акцентную кнопку альтернативного сценария для пользователя с разряженным телефоном.

#### Основной поток: номер и SMS-код

- Пользователь должен иметь возможность ввести номер телефона на экране ввода номера.
- Пользователь должен подтвердить номер кодом из SMS.
- Если код некорректен или просрочен, терминал должен показать ошибку и позволить запросить код повторно.

#### Основной поток: карта и оплата

- После подтверждения номера терминал должен показать инструкцию по карте и предложить приложить карту.
- Терминал должен показать состояние обработки оплаты после приложения карты.
- После успешной оплаты терминал должен показать экран успеха и инициировать выдачу powerbank.
- При ошибке оплаты терминал должен показать экран ошибки и позволить повторить попытку.

#### Упрощённый поток: разряженный телефон

- При нажатии кнопки альтернативного сценария терминал должен показать подсказку "Приложите карту для аренды".
- В упрощённом потоке терминал не должен запрашивать номер телефона или SMS-код.
- После успешной оплаты картой терминал должен выдать powerbank без создания аккаунта.

### Правила пользовательского поведения

- Powerbank не выдаётся, пока оплата не подтверждена как успешная.
- Основной поток всегда создаёт или находит аккаунт по номеру телефона перед привязкой карты.
- Упрощённый поток никогда не создаёт аккаунт.

### Ограничения и исключения на FE

- Критерии не фиксируют точный визуальный дизайн экранов терминала.
- Критерии не описывают flow возврата powerbank.
- Критерии не покрывают мультиязычность интерфейса.

## BE Criteria

### Затронутые backend области

- `gozap-backend`: создание/поиск аккаунта по номеру телефона, верификация SMS-кода, сохранение карты на аккаунт, создание заказа на оплату, обработка результата оплаты, инициирование выдачи powerbank, отправка SMS-уведомлений.
- Внешние интеграции: Stripe (оплата картой), Twilio (SMS-код и SMS-уведомления).

### Правила бизнес-логики и обработки

#### Создание аккаунта и верификация номера

- Backend должен отправлять одноразовый SMS-код через Twilio на введённый номер телефона.
- Backend должен создавать аккаунт по номеру телефона при первом успешном подтверждении кода, если аккаунта ещё нет.
- Backend должен находить существующий аккаунт по номеру телефона при повторном обращении.

#### Оплата и сохранение карты

- Backend должен обрабатывать оплату картой через Stripe для основного и упрощённого потока.
- В основном потоке backend должен сохранять карту в аккаунте пользователя для последующих аренд.
- В упрощённом потоке backend должен обработать разовую оплату без обязательной привязки к аккаунту.
- Backend не должен инициировать выдачу powerbank до подтверждения успешной оплаты от Stripe.

#### Уведомления

- После успешного создания аккаунта и/или начала аренды backend должен отправить SMS-уведомление пользователю через Twilio (основной поток).

### Побочные эффекты и интеграционные результаты

- Платежи: списание выполняется через Stripe в обоих потоках.
- Подписка / доступ: `N/A`
- Аналитика: Не определено.
- Email / CRM / webhooks: SMS-уведомления через Twilio; webhook Stripe о результате оплаты должен запускать выдачу powerbank.

### Ограничения и исключения на BE

- Критерии не фиксируют точный механический протокол выдачи powerbank станцией.
- Критерии не покрывают сценарий, когда оплата успешна, но станция не может физически выдать powerbank.
- Критерии не фиксируют точную схему хранения карты в Stripe (token/customer/payment method).

## Нефункциональные критерии

### FE

- Производительность: терминал должен показывать промежуточные состояния (ожидание SMS, обработка оплаты) без зависаний интерфейса.
- Доступность: понятные экраны ошибок для неверного кода и отклонённой карты.
- Консистентность UX: единый визуальный язык между основным и упрощённым потоком.

### BE

- Надежность: backend должен корректно обрабатывать повторные SMS-запросы и не создавать дублирующиеся аккаунты на один номер.
- Наблюдаемость: backend должен различать ошибки верификации SMS, ошибки оплаты Stripe и ошибки физической выдачи powerbank.
- Безопасность: данные карты обрабатываются через Stripe без хранения чувствительных данных карты в `gozap-backend`.

## Вне scope

- Flow возврата powerbank.
- Управление тарифами на терминале.
- Мультиязычность интерфейса терминала.
- Создание или изменение Qase test cases.

## Открытые вопросы

- Что происходит, если оплата прошла, но станция не выдала powerbank механически?
- Привязывается ли карта из упрощённого потока к аккаунту, если пользователь позже регистрируется тем же номером?
- Какая Stripe-схема используется для сохранения карты (Customer + PaymentMethod, SetupIntent и т.д.)?

## Примечания

- Критерии подготовлены на основе draft feature spec и входных SA-заметок (CSV) по приложению станций.
- `gozap-station-app` отвечает за экраны терминала и UX обоих потоков.
- `gozap-backend` отвечает за аккаунты, верификацию SMS, интеграцию со Stripe и Twilio.
