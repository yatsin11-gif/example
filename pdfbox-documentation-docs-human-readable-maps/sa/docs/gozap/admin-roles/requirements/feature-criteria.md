# Критерии

## Источник

- Feature spec: `sa/docs/gozap/admin-roles/requirements/feature-spec.md`
- Утвердил: Не утверждено; draft подготовлен по запросу SA
- Дата: 2026-06-30
- Репозитории в скоупе: `gozap-admin`, `gozap-backend`

## Цель

- Супер-админ должен иметь возможность создавать админов с заданным уровнем доступа.
- Поставка считается корректной, если админ видит только разделы, доступные его уровню.

## FE Criteria

### Затронутые поверхности

- `gozap-admin`: создание админа, выбор уровня доступа, навигация по разделам с учётом доступа.

### Пользовательские сценарии и состояния

#### Создание админа (супер-админ)

- Супер-админ должен иметь возможность создать нового админа.
- Супер-админ должен выбрать уровень доступа для нового админа при создании.

#### Вход и навигация (админ)

- Админ должен иметь возможность войти в админку.
- После входа админ должен видеть только разделы, доступные его уровню доступа.
- Разделы, недоступные уровню админа, не должны отображаться в навигации.

### Правила пользовательского поведения

- Уровень доступа определяет видимый набор разделов; супер-админ видит все разделы.
- Только супер-админ может создавать новых админов.

### Ограничения и исключения на FE

- Критерии не фиксируют точный список и количество уровней доступа кроме супер-админ/админ.
- Критерии не требуют гранулярных прав на уровне действий внутри раздела.

## BE Criteria

### Затронутые backend области

- `gozap-backend`: модель ролей/уровней доступа, привязка уровня доступа к админу, проверка доступа к разделам на каждом запросе.
- Внешние интеграции: `N/A`

### Правила бизнес-логики и обработки

#### Управление ролями

- Backend должен хранить роль/уровень доступа для каждого админа.
- Backend должен разрешать создание нового админа только запросу от супер-админа.

#### Проверка доступа

- Backend должен отклонять запросы к разделам, не входящим в уровень доступа админа.
- Backend должен явно различать роль "супер-админ" и роль "админ" при авторизации запроса.

### Побочные эффекты и интеграционные результаты

- Платежи: `N/A`
- Подписка / доступ: уровень доступа определяет видимость разделов админки, включая партнёрский раздел (`sa/docs/gozap/partners-admin`).
- Аналитика: Не определено.
- Email / CRM / webhooks: `N/A`

### Ограничения и исключения на BE

- Критерии не фиксируют точную модель прав (RBAC-таблицы, enum уровней).
- Критерии не покрывают аудит-лог действий админов.

## Нефункциональные критерии

### FE

- Производительность: навигация должна формироваться по уровню доступа без видимой задержки.
- Доступность: понятное сообщение при попытке открыть недоступный раздел напрямую по ссылке.
- Консистентность UX: единый паттерн скрытия недоступных разделов для всех уровней.

### BE

- Надежность: проверка доступа должна выполняться на backend, а не только скрывать разделы на FE.
- Наблюдаемость: backend должен логировать попытки доступа к запрещённым разделам.
- Безопасность: создание админа и назначение уровня доступа должно быть доступно только супер-админу.

## Вне scope

- Гранулярные права на уровне отдельных действий.
- Аудит-лог действий админов.
- Самостоятельное изменение уровня доступа админом.
- Создание или изменение Qase test cases.

## Открытые вопросы

- Сколько уровней доступа должно существовать кроме супер-админ и админ?
- Может ли существовать более одного супер-админа?
- Какие конкретные разделы (включая партнёрский) входят в каждый уровень доступа?

## Примечания

- Критерии подготовлены на основе draft feature spec и входных SA-заметок (CSV) по ролям в админке.
- `gozap-admin` отвечает за UI создания админов и навигацию по уровню доступа.
- `gozap-backend` отвечает за модель ролей и проверку доступа на каждом запросе.
