# Критерии

## Источник

- Feature spec: `sa/docs/gozap/auth/requirements/feature-spec.md`
- Утвердил: Не утверждено; draft подготовлен по запросу SA
- Дата: 2026-06-30
- Репозитории в скоупе: `gozap-station-app`, `gozap-backend`

## Цель

- Пользователь должен получать автоматически вставленный код подтверждения из SMS без ручного набора.
- Поставка считается корректной, если автоматическая вставка работает там, где платформенно доступна, и не блокирует ручной ввод иначе.

## FE Criteria

### Затронутые поверхности

- `gozap-station-app`: поле ввода SMS-кода на экране терминала (основной поток аренды, `sa/docs/gozap/terminal-rental-app`).
- `gozap-admin`: поле ввода SMS-кода при сбросе пароля партнёра (`sa/docs/gozap/partners-admin`).

### Пользовательские сценарии и состояния

#### Автоматическая вставка кода

- При получении SMS-кода поле ввода должно автоматически заполниться кодом, если платформа терминала это поддерживает.
- Если автоматическая вставка недоступна, пользователь должен иметь возможность ввести код вручную без потери функциональности.

#### Повторный запрос кода

- Пользователь должен иметь возможность запросить повторную отправку кода, если код не пришёл или истёк.

### Правила пользовательского поведения

- Автоматическая вставка не должна требовать от пользователя дополнительных действий, кроме получения SMS.
- Ручной ввод кода остаётся доступен как fallback всегда.

### Ограничения и исключения на FE

- Критерии не фиксируют конкретный технический механизм autofill для платформы терминала.
- Критерии не покрывают подтверждение через push или email.

## BE Criteria

### Затронутые backend области

- `gozap-backend`: генерация и отправка одноразового кода, ограничение срока жизни и числа попыток, верификация кода.
- Внешние интеграции: Twilio.

### Правила бизнес-логики и обработки

#### Генерация и отправка кода

- Backend должен генерировать одноразовый SMS-код и отправлять его через Twilio на указанный номер телефона.
- Backend должен ограничивать частоту повторной отправки кода на один номер.

#### Верификация кода

- Backend должен принимать код только в течение ограниченного срока жизни.
- Backend должен ограничивать число попыток ввода неверного кода.
- После истечения срока жизни или превышения числа попыток backend должен требовать новый код.

### Побочные эффекты и интеграционные результаты

- Платежи: `N/A`
- Подписка / доступ: подтверждение по SMS-коду является предусловием для основного потока аренды и сброса пароля партнёра.
- Аналитика: Не определено.
- Email / CRM / webhooks: SMS отправляется через Twilio.

### Ограничения и исключения на BE

- Критерии не фиксируют точный срок жизни кода и число попыток.
- Критерии не покрывают альтернативные провайдеры SMS.

## Нефункциональные критерии

### FE

- Производительность: автозаполнение должно происходить сразу после получения SMS без задержки от пользователя.
- Доступность: ручной ввод кода доступен как fallback на всех поддерживаемых устройствах.
- Консистентность UX: одинаковое поведение поля ввода кода в терминале и в админке (сброс пароля).

### BE

- Надежность: повторные запросы кода не должны создавать дублирующиеся активные коды для одного номера.
- Наблюдаемость: backend должен логировать неуспешные попытки верификации кода.
- Безопасность: код одноразовый, с ограниченным сроком жизни и ограниченным числом попыток ввода.

## Вне scope

- Подтверждение через push или email.
- Смена провайдера SMS.
- Создание или изменение Qase test cases.

## Открытые вопросы

- Каков точный срок жизни кода и максимальное число попыток ввода?
- Поддерживает ли платформа терминала нативный SMS autofill, или нужен альтернативный механизм (например, голосовой ввод)?

## Примечания

- Критерии подготовлены на основе draft feature spec и входных SA-заметок (CSV) по авторизации через SMS.
- Эта фича — общая зависимость для `terminal-rental-app` (подтверждение номера) и `partners-admin` (сброс пароля).
- `gozap-backend` отвечает за генерацию, отправку через Twilio и верификацию кода.
