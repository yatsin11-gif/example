# Критерии

## Источник

- Feature spec: `sa/docs/editor/ocr-editable-documents/requirements/feature-spec.md`
- Утвердил: SA
- Дата: 2026-05-05
- Репозитории в скоупе: `pdf.box-app`, `pdfbox-backend`

## Цель

- Пользователь в editor flow должен иметь возможность выбрать страницу и область документа и получить server-side обработанный результат, пригодный для подмены страницы и дальнейшей работы с распознанным текстом.
- Поставка считается корректной, если edit OCR работает как отдельный flow по выделенной области и не требует от фронта дополнительной локальной очистки или подмены фона.

## FE Criteria

### Затронутые поверхности

- `pdf.box-app`: editor flow с выделением области на странице, запуском edit OCR request и получением результата для подмены страницы.
- `pdf.box-admin`: `N/A`
- `pdf.box-landing`: `N/A`

### Пользовательские сценарии и состояния

#### Selected area submitted for edit OCR

- Пользователь может выбрать страницу документа и выделить область для обработки.
- Пользователь должен иметь возможность выбрать OCR language перед запуском edit OCR.
- Фронт должен передавать в backend номер страницы, координаты выделенной области и выбранный OCR language.
- Если editor flow открыт для guest document, frontend должен использовать guest edit OCR transport без смены пользовательского сценария.
- После успешной server-side обработки пользователь получает результат, пригодный для подмены страницы в editor flow.

#### Selected area returns editable result

- Если выбранная область находится в поддерживаемом editable scope, пользователь получает результат, в котором распознанный текст этой области может использоваться для дальнейшего редактирования.
- Результат должен позволять фронту подменить страницу без дополнительной локальной очистки или фоновой обработки.
- Нередактируемые графические и декоративные элементы вокруг распознанного текста могут оставаться частью фонового слоя результата.

#### Selected area returns fallback result

- Если backend не может надежно обработать выбранную область в рамках поддерживаемого scope, пользователь должен получить явный fallback product behavior.
- Fallback не должен требовать от фронта локальной реконструкции страницы.
- Переход пользователя внутри editor flow должен оставаться консистентным для success и fallback-сценариев.

### Правила пользовательского поведения

- Пользователь должен запускать этот flow через выделенную область страницы, а не через общий document OCR flow.
- Пользовательский выбор OCR language должен быть явной частью edit OCR user flow.
- Пользовательский сценарий edit OCR должен оставаться консистентным для workspace и guest document contexts.
- Пользователь должен получать editable behavior только для той области, которую backend успешно обработал как распознанный редактируемый текст.
- Пользователь не должен получать результат, требующий дополнительной локальной очистки или фоновой подмены на фронте.
- Для поддерживаемых сценариев итоговая подмененная страница должна оставаться приемлемо похожей на исходную визуально.
- Для неподдерживаемых сценариев продукт должен отрабатывать через явный fallback в editor flow.
- FE не должен расширять scope до `pdf.box-admin` или `pdf.box-landing` в рамках этой итерации.

### Ограничения и исключения на FE

- Первая итерация не требует превращать все визуальные элементы документа в редактируемые объекты.
- Первая итерация не требует гарантии полного визуального совпадения reconstructed документа с оригиналом.
- FE не должен брать на себя локальную очистку фона или дополнительную локальную подготовку страницы.
- Поведение для сложных документов, отдельных зон и fallback-состояний должно быть ограничено только подтвержденным product scope.

## BE Criteria

### Затронутые backend области

- `pdfbox-backend`: создание request на edit OCR обработку, запуск новой Lambda и возврат результата в editor flow.
- Внешние интеграции: Lambda processing, `TempBucket`, OCR/reconstruction components и Gemini для font-related metadata.

### Правила бизнес-логики и обработки

#### Request and processing bootstrap

- Backend должен принимать от фронта номер страницы, координаты выделенной области и выбранный OCR language.
- Backend должен создавать request на обработку edit OCR и запускать для этого новую Lambda.
- Lambda должна скачать исходный документ или нужную страницу, вырезать указанную область, выполнить OCR с учетом выбранного OCR language, сохранить артефакты в `TempBucket` и вернуть результат обратно в backend.
- Backend должен поддерживать edit OCR request как минимум через два API entrypoints: workspace-scoped и guest-scoped, если документ относится к соответствующему context.

#### Editable result assembly

- Backend должен формировать результат так, чтобы поддерживаемый распознанный текст был пригоден для дальнейшего редактирования в текущем editor engine.
- После запуска базового OCR flow Lambda должна подготавливать очищенный или подмененный фон для обработанной страницы или области.
- Результат Lambda должен позволять фронту подменить страницу без дополнительной локальной обработки.
- Нередактируемые графические элементы, печати, подписи и декоративные части документа могут оставаться в составе фонового слоя результата.

#### Font metadata enrichment

- После запуска базового OCR flow Lambda должна отправлять вырезанный блок в Gemini и получать дополнительные данные по шрифтам и связанным характеристикам текста.
- На первой итерации прямой вызов Gemini из Lambda считается допустимым product-approved способом.
- Возможное последующее вынесение Gemini-вызова в отдельный jobs module не должно менять пользовательский сценарий.

#### Обработка документов вне editable scope

- Если документ, страница или выделенная область не могут быть надежно обработаны в рамках поддерживаемого scope, backend должен возвращать результат, совместимый с fallback product behavior.
- Для таких кейсов backend не должен перекладывать на фронт локальную реконструкцию страницы.
- Обработка сложных документов может отличаться от обработки простых документов только после явного подтверждения product scope в следующих артефактах.

#### Scope первой итерации

- Первая итерация может покрывать не все document classes, не все OCR languages и не все размеры выделенной области, если эти ограничения явно зафиксированы в последующих согласованных артефактах.
- Этот flow не должен трактоваться как общий document OCR flow; OCR здесь используется как первый этап определения места подмены фона и распознавания текста для вставки в итоговый документ.
- Backend не должен добавлять в результат новые редактируемые элементы, которые не относятся к распознанному пользовательскому тексту выбранной области.
- Guest support для edit OCR входит в scope первой итерации и не должен оставаться неявным техническим расширением вне согласованных артефактов.

### Побочные эффекты и интеграционные результаты

- Платежи: `N/A`
- Подписка / доступ: `N/A`
- Аналитика: backend должен поддержать передачу данных, необходимых для измерения запуска edit OCR по выделенной области, успешности обработки и использования success/fallback сценариев.
- Email / CRM / webhooks: `N/A`

### Ограничения и исключения на BE

- Критерии не фиксируют конкретный внутренний способ OCR, очистки фона или реконструкции beyond подтвержденного solution shape с Lambda, `TempBucket` и Gemini.
- Критерии не требуют поддержки всех сложных документов первой итерацией.
- Критерии не вводят новую бизнес-логику для `pdf.box-admin`, `pdf.box-landing` или внешних каналов коммуникации.

## Нефункциональные критерии

### FE

- Производительность: edit OCR не должен вводить editor flow, в котором обработка выделенной области становится непригодной для пользовательского сценария замены страницы.
- Доступность: fallback должен быть доступен пользователю в тех случаях, когда editable result недоступен в рамках поддерживаемого scope.
- Консистентность UX: editor flow должен явно различать success и fallback состояния и не должен создавать ложное ожидание связи этого сценария с общим document OCR flow.

### BE

- Надежность: backend должен стабильно возвращать либо результат edit OCR для выделенной области в поддерживаемом scope, либо корректный fallback без поломки editor flow.
- Наблюдаемость: решение должно позволять измерять запуск edit OCR, обработку Lambda, сохранение артефактов и использование success/fallback сценариев.
- Безопасность: `N/A` на уровне product criteria; дополнительные требования могут быть определены на этапе implementation planning при появлении новых интеграций.

## Вне scope

- Полная визуальная реконструкция документа 1:1 для всех документов и страниц.
- Превращение всех графических, декоративных и служебных элементов документа в редактируемые объекты.
- Вынесение Gemini-вызова в отдельный jobs module в первой итерации.
- Выбор альтернативного backend orchestration вне подтвержденной схемы `backend -> Lambda -> TempBucket -> backend`, если такая схема не будет отдельно пересмотрена.
- Изменения в `pdf.box-admin` и `pdf.box-landing`.

## Открытые вопросы

- Должен ли первый rollout ограничиваться только выбранной областью или обязан сразу возвращать готовый результат для подмены всей страницы вокруг этой области?
- Какой fallback product behavior должен видеть пользователь, если backend не может подготовить корректный результат для выделенной области?
- Какие document classes, OCR languages и размеры выделенной области входят в обязательный scope первой итерации?
- Какие именно font-related характеристики обязаны возвращаться из Gemini в первой итерации?
- Какой уровень визуального отклонения от оригинала допустим для server-side подмененной страницы или области?

## Примечания

- Критерии обновлены с учетом подтвержденного solution shape: фронт передает страницу и координаты области, backend запускает Lambda, артефакты сохраняются в `TempBucket`, а Gemini вызывается напрямую из Lambda на первой итерации.
