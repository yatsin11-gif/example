## Проблема

- Пользователи в editor-сценарии ожидают возможность изменить текст внутри уже существующей страницы документа, но текущий продукт не умеет превращать выбранную область страницы в редактируемый результат.
- Текущая OCR-реализация документа не решает задачу локальной подмены фона и вставки распознанного текста в конкретную область страницы.
- Без отдельного edit OCR flow пользователь не может получить редактируемый результат для выбранного блока документа без ручной локальной обработки на фронте.
- Эта проблема актуальна как для workspace documents, так и для guest documents, если editor flow доступен в обоих контекстах.

## Цель

- Дать пользователю в editor flow возможность выбрать область на конкретной странице и получить результат, пригодный для подмены этой страницы и последующего редактирования распознанного текста.
- Перенести OCR, подготовку фона и сбор дополнительных данных о шрифте в backend pipeline, чтобы фронту не требовалась дополнительная локальная обработка страницы.

## Не входит в текущую итерацию

- Полная гарантия визуального совпадения reconstructed документа с оригиналом 1:1.
- Превращение всех визуальных элементов документа в редактируемые объекты.
- Jira decomposition, implementation design и выбор финального технического pipeline.
- Вынесение Gemini-вызова в отдельный jobs module в первой итерации.
- Изменения в `pdf.box-admin` и `pdf.box-landing`, если для них не появится отдельная подтвержденная потребность.

## Триггер и аудитория

- Точка входа / триггер: пользователь в editor flow выбирает страницу и выделяет область, которую хочет обработать для редактирования текста.
- Основная аудитория: пользователи editor flow, которым нужно изменить текст в конкретном блоке документа.
- Вторичная аудитория: пользователи, которым потенциально понадобится замена всей страницы после server-side обработки выбранной области.

## Целевое поведение продукта

### Сценарий

1. Пользователь в editor flow выбирает страницу документа, выделяет область, которую нужно обработать, и выбирает язык OCR.
2. Фронт передает номер страницы, координаты выделенной области и выбранный OCR language в backend.
3. Backend запускает edit OCR обработку для этой области, получает распознанный текст и артефакты, достаточные для подмены страницы без дополнительной локальной обработки на фронте.
4. Если выбранная область попадает в поддерживаемый editable scope, пользователь получает результат для подмены страницы и дальнейшей работы с распознанным текстом; если нет, продукт отрабатывает через явный fallback.

### Правила результата

- Editable behavior должен появляться именно в той выделенной области страницы, которую продукт успешно обработал как распознанный редактируемый текст.
- Пользовательский выбор OCR language должен использоваться именно для того edit OCR request, который запускается для выбранной области.
- Backend должен возвращать результат, который позволяет фронту подменить страницу без дополнительной локальной очистки или подмены фона.
- Визуальный результат после обработки выделенной области не должен заметно деградировать относительно исходной страницы сверх допустимого уровня для первой итерации.
- Нередактируемые графические элементы, печати, подписи и декоративные части документа могут оставаться частью фона.
- Для кейсов вне поддерживаемого editable scope продукт должен отработать через fallback без требования локальной post-processing логики на фронте.
- На первом этапе OCR в этом сценарии используется как служебный шаг для определения места подмены фона и распознавания текста для вставки в итоговый документ, а не как document OCR flow.

## Бизнес-правила

- Этот edit OCR flow не является продолжением или разновидностью document OCR flow; OCR здесь используется как первый этап подготовки редактируемого результата для выделенной области.
- Источником запроса в backend являются номер страницы, координаты выделенной области и выбранный пользователем OCR language, которые передает фронт.
- Первая итерация должна поддерживать edit OCR request как для workspace document flow, так и для guest document flow, если документ открыт в соответствующем editor context.
- Не каждый элемент страницы обязан становиться редактируемым; допускается сохранение части контента как фонового слоя после server-side обработки.
- На первом этапе backend может вызывать Gemini напрямую из Lambda для получения данных о шрифте и связанных характеристиках текста.
- Приоритетом первой итерации является приемлемый баланс между редактируемостью, качеством подмененной страницы, latency и скоростью поставки, а не финальная архитектурная изоляция всех внешних вызовов.

## Ограничения и известные лимитации

- Продукт / UX: подтвержден user-trigger через выделенную область страницы, но детальный fallback UX для неподдерживаемых кейсов пока не определен.
- Биллинг / правовые ограничения: Не определено.
- Технические ограничения, уже подтвержденные на продуктовом уровне: backend должен создать request и запустить новую Lambda; Lambda должна скачать исходный документ или страницу, вырезать нужную область, выполнить OCR с учетом выбранного пользователем языка, сохранить артефакты в `TempBucket` и вернуть результат в backend; после запуска базового OCR flow Lambda должна также готовить очищенный или подмененный фон для страницы или области и получать из Gemini дополнительные данные по шрифтам и связанным характеристикам текста.
- Внешние зависимости: результат должен быть совместим с текущим editor engine; pipeline зависит от качества OCR, качества server-side очистки или подмены фона и доступности Gemini для расширенных font metadata.

## Пограничные сценарии

- Пользователь выделяет область на конкретной странице, но backend не может надежно подготовить результат для подмены страницы.
- Пользователь выбирает OCR language, который не входит в поддерживаемый scope первой итерации или дает низкое качество распознавания для конкретного блока.
- Пользователь запускает edit OCR для guest document, и backend должен отработать тот же сценарий без зависимости от workspace-only contract.
- Документ является фотографией с перекосом, перспективным искажением или лишним фоном вокруг листа.
- Документ содержит таблицы, печати, подписи или декоративные элементы рядом с редактируемым текстом.
- Распознан текст на неоднородном фоне, где очистка фона может повлиять на визуальное качество.
- Вызов Gemini возвращает неполные или неточные данные о шрифте и связанных характеристиках текста.

## История изменений

### 2026-05-05

- Создан первый feature spec на основе PRD по editable OCR и technical research по zone reconstruction и selective reconstruction.
- Уточнено, что первая итерация относится к отдельному edit OCR flow по выделенной области страницы, использует backend request + Lambda + `TempBucket`, а Gemini вызывается напрямую из Lambda.

## Допущения

- Первая итерация строится вокруг user-selected area, а не вокруг полного document OCR conversion.
- Первая итерация может покрывать не все типы документов, не все языки и не все размеры выделенной области, если это явно отражено в criteria.
- Пользовательский выбор OCR language происходит на FE и передается в backend как часть edit OCR request.
- Workspace и guest flows должны использовать один product scenario с разными API entrypoints, а не два разных user сценария.
- `pdf.box-app` и `pdfbox-backend` являются основными репозиториями в scope до появления подтвержденной потребности в других репозиториях.
